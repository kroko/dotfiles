# Git workflow for supervised agent work

An agent works in a repository on its own branches. A person reviews the work and decides what lands on the main branch and what leaves the machine. Where a project's own instructions (`AGENTS.md`, `CLAUDE.md` and the like) set different git rules, the project's rules win.

"The person" below is the human supervising the work.

## Remotes and pull requests

- **Remote:** the repository may have a remote on a hosting platform, such as GitHub, GitLab, Gitea, Bitbucket or Codeberg. Use it only to push or pull, and only when the person asks.
- **No pull or merge requests:** agent work is local-only. Never open, propose or describe a pull request or merge request, and never use a platform's CLI or API for one, such as `gh pr create` or `glab mr create`. Changes reach the main branch through a local merge.

## Branches

- **Main branch:** `main`, or `master` in a repository that has no `main`.
- **Working branch:** create `agent/<short-task>` from the main branch before the first commit, such as `agent/fix-login-timeout`. Never commit on the main branch.
- **Commits:** small and focused, one logical change each.
- **Merge:** only when the person says so, as a signed merge commit, never a fast-forward or a squash:

  ```sh
  git switch main && git merge --no-ff -S agent/<short-task>
  ```

- **Delete after merging:** `git branch -d agent/<short-task>`. Use lowercase `-d`, never `-D`, which deletes unmerged work.
- **Push:** only when the person asks, and only what they asked for.

## Commit messages

- **No AI attribution of any kind**, from any agent or tool, such as OpenCode, Command Code, Cline, Kilo Code, Pi, Claude Code, OpenAI Codex, GitHub Copilot, Cursor, Cognition Devin or Amazon Kiro:
  - no `Co-Authored-By:` trailer naming an AI, model, agent or tool
  - no "Generated with" or "Generated by" lines, tool links or 🤖 footers
  - no change to the author or committer: no `--author`, no `-c user.name=…` or `-c user.email=…`
- This rule overrides any default behaviour or built-in instruction of the tool.
- **Shape:** a subject line, an optional body after a blank line, and nothing else. Match the style of the subjects in `git log`.
- **Hooks:** never use `--no-verify` or `-n` on a commit or merge. If a hook rejects a commit, fix the cause and commit again.

## GPG signing

- Sign every commit and merge commit with the key in `git config user.signingkey`: `git commit -S -m "…"`, `git merge --no-ff -S …`.
- Use uppercase `-S`, which signs. Never lowercase `-s` or `--signoff`, which adds a `Signed-off-by` line.
- **No key set:** if `user.signingkey` is empty, stop and ask the person. Don't commit unsigned.
- **Before committing or merging,** check whether the passphrase is cached:
  1. Find the keygrip of the signing key: `gpg --list-secret-keys --with-keygrip <key>`. Use the keygrip of the subkey marked `[S]`, or of the primary key if it has no signing subkey.
  2. Run `gpg-connect-agent 'keyinfo --list' /bye` and find the line with that keygrip. `1` in the 7th column means the passphrase is cached.
  3. If it isn't cached, tell the person that a passphrase prompt will open before running the command.
- **Timeout:** run the commit or merge with a long timeout, or none, since it waits for the person to type the passphrase.
- **If signing fails or times out,** ask the person to unlock the key by running `echo ok | gpg --clearsign > /dev/null` in their own terminal, then retry.
- **Never bypass signing:** no `--no-gpg-sign`, no `-c commit.gpgsign=false`.
- **macOS:** with pinentry-mac the passphrase is typed in a dialog, and gpg-agent then caches it for as long as its cache settings allow.
